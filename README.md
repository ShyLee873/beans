# Beans

Beans is a small virtual pet application built with **Elixir, Phoenix LiveView, and JavaScript**.

I started the project as a way to learn Elixir by building something where I could visualize state change over time. Instead of working through isolated syntax exercises, I wanted a project that would let me experiment with processes, pattern matching, immutable state, PubSub, LiveView, and browser-side JavaScript in the same application.

The result is Beans: a database-free virtual cat whose hunger, energy, happiness, sleep state, mood, and increasingly dramatic visual representation are managed across a GenServer, Phoenix LiveView, and a couple of external APIs.

## What Beans Does

Beans maintains an in-memory state containing:

```elixir
%{
  name: "Beans",
  hunger: 20,
  energy: 80,
  happiness: 75,
  sleeping: false
}
```

That state changes through user interaction and timed events.

The user can:

- Feed Beans
- Play with Beans
- Pet Beans
- Watch his hunger, energy, and happiness change
- See his mood respond to combinations of those values
- Receive a mood-appropriate cat GIF through the GIPHY API
- Receive rotating quotes through the QuoteSlate API (which you can check out [here](https://github.com/musheer360/QuoteSlate))

Beans also sleeps when his energy is depleted, whether it's a cozy snooze or an angry nap depends on the user's choices.

## Architecture

The application is intentionally small, but it gave me a chance to work with several important Elixir and Phoenix concepts together.

### GenServer State

`Beans.Pet` owns the pet state.

Actions such as feeding, playing, and petting Beans are sent through the GenServer API rather than modifying UI state directly.

Conceptually:

```text
User action
    ↓
Phoenix LiveView
    ↓
Beans.Pet GenServer
    ↓
New immutable state
    ↓
Phoenix PubSub
    ↓
LiveView receives :pet_updated
    ↓
UI rerenders
```

The GenServer remains the source of truth for Beans' state.

### Mood Matching

Beans' mood is determined in Elixir using pattern matching and guards.

For example:

```elixir
defp mood(%{hunger: hunger}) when hunger >= 80,
  do: %{
    text: "Beans is hungry",
    gif_query: "hungry cat"
  }
```

More specific conditions are placed before broader ones so that mood priority is controlled by function-clause order.

This allows the same state evaluation to provide both:

- Human-readable UI text
- A search query for the visual representation of that mood

JavaScript never decides how Beans feels. Elixir does.

### PubSub + LiveView

When the pet state changes, the GenServer broadcasts the new state through Phoenix PubSub.

The LiveView subscribes to the pet topic:

```elixir
Phoenix.PubSub.subscribe(Beans.PubSub, "pet:beans")
```

and handles updates with:

```elixir
def handle_info({:pet_updated, pet}, socket) do
  {:noreply, assign(socket, :pet, pet)}
end
```

This keeps the interface synchronized with the GenServer without introducing client-side state management.

## JavaScript Hooks

JavaScript is used for browser-specific behavior rather than application state.

### `BeansMood`

The `BeansMood` LiveView hook reads the mood query generated by Elixir:

```html
data-query="hungry cat"
```

and uses it to request a GIF from GIPHY.

The flow is:

```text
Elixir mood rules
    ↓
gif_query
    ↓
HEEx data attribute
    ↓
BeansMood LiveView hook
    ↓
GIPHY API
    ↓
Cat GIF
```

If the API request fails, the original Elixir-rendered emoji remains available as a fallback.

### `BeansQuote`

A separate `BeansQuote` hook requests a quote from QuoteSlate on its own timer.

```javascript
this.timer = setInterval(() => {
  this.getQuote();
}, 30_000);
```

The timer is cleaned up when the LiveView hook is destroyed:

```javascript
destroyed() {
  clearInterval(this.timer);
}
```

Keeping the hooks separate means that they respond to different events:

```text
BeansMood
→ triggered by changes to Beans' state

BeansQuote
→ triggered by its own browser-side timer
```

Neither API is responsible for application state and are integrated for the sole reason that "I felt like it".

## API Configuration

Beans currently uses the GIPHY API for mood GIFs.

For local development, create a `.env` file:

```bash
GIPHY_API_KEY=your_api_key_here
```

Make sure `.env` is excluded from source control:

```gitignore
.env
```

Load the environment variable before starting Phoenix:

```bash
set -a
source .env
set +a

mix phx.server
```

Phoenix reads the value in `config/runtime.exs`:

```elixir
giphy_api_key =
  System.get_env("GIPHY_API_KEY") ||
    raise "GIPHY_API_KEY environment variable is missing"

config :beans, :giphy_api_key, giphy_api_key
```

## Running Beans Locally

Clone the repository:

```bash
git clone https://github.com/ShyLee873/beans.git
cd beans
```

Install dependencies:

```bash
mix setup
```

Load the GIPHY API key:

```bash
set -a
source .env
set +a
```

Start Phoenix:

```bash
mix phx.server
```

Then visit:

```text
http://localhost:4000
```

## Why I Built It

I primarily work with object-oriented languages, particularly Ruby, so one of my goals with Beans was to become more comfortable thinking in terms of:

- Immutable state
- Pattern matching
- Function clauses
- Processes
- Message passing
- Functional transformations
- Server-rendered reactive interfaces

A virtual pet turned out to be a useful model for learning those concepts because state transitions are visible immediately.

When Beans becomes hungry, tired, happy, or neglected, I can trace the entire transition from the GenServer state through PubSub and LiveView to what eventually appears in the browser.

It has also given me a small environment where I can break things, inspect what happened, and understand why the fix works rather than simply following a tutorial.
